What Is Quarkus?

Supersonic Subatomic Java

The official tagline. What does it actually mean?

A Stack for Writing Java Applications

Cloud Native

  • Fast startup
  • Low memory usage
  • Containers and Kubernetes

Enterprise

  • Transactions, security
  • Health, metrics, tracing
  • Fault tolerance

Built on APIs you may already know: Jakarta REST, CDI, Jakarta Persistence, MicroProfile

  • Quarkus is a Java stack, not an app server. You don't deploy a WAR into something; the runtime is built into your application.
  • Cloud native: it was built for containers, where startup time and memory cost money. Think scaling up fast, or many instances on one node.
  • Enterprise: what you'd expect from an app server is still here. Many are the same projects WildFly uses: Narayana for transactions, Hibernate, SmallRye for MicroProfile.
  • Each capability is an extension you add.
  • Not only for microservices: CLIs, batch jobs, Kubernetes operators, monoliths too.
  • Bottom line: same APIs, different moment when the work happens.

Build-Time Principle

Being fast by doing less at startup

Work Traditional container Quarkus
Parse configuration Startup Build
Scan the classpath for annotations Startup Build
Wire beans and resolve injection points Startup Build
Generate proxies Startup Build
Start the application Startup Startup
When does the work happen?

With a traditional application server, the server parses the configuration, processes the deployment, then starts the deployment.

In Quarkus, the processing happens at build time leaving only the start of the services when starting. Generally speaking, that means fewer classes loaded, less reflection and less memory.

You fail quicker with Quarkus. You see most failures at build time, rather than runtime.

JVM or Native

JVM

  • Well-known, mature
  • JIT, best peak performance
  • Slower startup, more memory

Native

  • Very fast startup
  • Low memory usage
  • No JIT, longer builds
  • Reflection may need registration
  • Same code, same app. You choose JVM or native when you package, not when you write it.
  • JVM mode is the default and what most people run.
  • Native is built with GraalVM/Mandrel. It follows from the build-time principle: Quarkus already did the work at build time, so native compilation is the next step.
  • Extensions handle most of the native configuration, like registering reflection, for you.
  • When to pick native: fast scale-up, scale to zero, CLIs. When to stay on the JVM: long-running services where the JIT's peak throughput matters. 
./mvnw package            # JVM
./mvnw package -Dnative   # native
./mvnw package -Dnative -Dquarkus.native.container-build=true   # no local GraalVM

Too Much Magic?

Magic is not inherently bad. Magic is power that can be used for good or for bad. […] There is magic, it's just magic you have enough knowledge (or trust) of vs. magic you don’t.

Clément Escoffier, quarkus.io/blog/magic-control

Every framework in the room has magic, Spring Boot auto-configuration included. The point is knowing where it happens. In Quarkus, it happens at build time, so you can inspect it. You'll see it in the Dev UI in the first demo.

Bringing the Tasks App Over

New project, dev mode, bring HealthResource over, live reload, Dev UI.

mkdir demo && cd demo
quarkus create app dev.jperkins.example:tasks --extension=rest-jsonb
cd tasks && mvn quarkus:dev

Copy in HealthResource and open /status: the same Jakarta REST code runs. Then add MicroProfile Health:

quarkus ext add smallrye-health
quarkus ext add hibernate-orm hibernate-validator jdbc-h2

Open /q/health (also /q/health/live, /ready, /started), then delete HealthResource: less code to own.

Mention: quarkus dev, ./mvnw quarkus:dev, code.quarkus.io, Gradle.

Dev mode keys: d opens the Dev UI, r runs the tests, h lists the rest.

Data and Dev Services

On WildFly the data source came from a Galleon layer and java:comp/DefaultDataSource. Here, add the driver extension and Dev Services starts the database.

A little bit about Dev Services. In dev and test mode, if an extension needs a service (a database, Kafka, Keycloak, Redis) and you haven't configured its URL, Quarkus starts one for you and wires in the connection settings. Usually that's a container (Docker or Podman); H2 runs in-process, which is what this demo uses. Nothing starts in production; there you configure the real service. 

quarkus ext add hibernate-orm hibernate-validator jdbc-h2

Copy in the app's classes from February: model, data and resources packages.

No persistence.xml. Point at the log line: Quarkus sets drop-and-create itself because Dev Services owns the database. For production, set it explicitly: 

%prod.quarkus.datasource.jdbc.url=jdbc:h2:mem:tasks;DB_CLOSE_DELAY=-1
%prod.quarkus.hibernate-orm.schema-management.strategy=create

The persistence.xml still works (mainly for migrations), but it always uses the default data source, you may need to set the dialect yourself, and it can't be mixed with quarkus.hibernate-orm.* properties (that's an exception).

Copy the UI: src/main/webapp moves to src/main/resources/META-INF/resources (index.html and resources/main.js). No WAR, so static files are served from the classpath. Open the UI.

With Postgres the only change is the extension (jdbc-postgresql), and Dev Services starts a container for you.

Reopen /q/health/ready: the database check is there with no code, just from adding the extension.

What Doesn't Carry Over

  • CDI Full features such as portable extensions
  • The contents of beans.xml
  • JNDI lookups
  • Changing settings at runtime

beans.xml still marks a bean archive, but its content is ignored, so alternatives are selected with @Priority.

  • Use Build Compatible Extensions instead of CDI portable extensions
  • Some properties are baked in at build time, for example database config. Setting them when you start the app is ignored with a warning; you have to rebuild. The config tables in each guide mark these with a lock icon.

Now That You’re Here: Jakarta Data

Plain JPA


@Inject
private EntityManager em;

public Collection<Task> getTasks(final boolean completed) {
    return em.createNamedQuery("findCompleted", Task.class)
            .setParameter("completed", completed)
            .getResultList();
}

public Task getTaskById(final long id) {
    return em.find(Task.class, id);
}

Jakarta Data, with Quarkus Data Hibernate


@Repository
public interface TaskRepository {

    @Query("where completed = :completed order by priority, added, summary")
    List<Task> getTasks(boolean completed);

    @Find
    Optional<Task> getTaskById(Long id);
}

Experimental since Quarkus 3.37, ships in Quarkus 4.0. Panache is still supported.

  • The standard Jakarta EE 11 repository: an interface, implementation generated at compile time, queries type-checked against the entity. The Task entity doesn't change.
  • Story: Quarkus created Panache because there was no standard repository pattern. Jakarta Data standardized it, so Quarkus rebuilt on the spec. Quarkus Data is the new entry point; Panache 1 stays supported, but new investment goes to Quarkus Data.
  • Add it with: quarkus ext add quarkus-data-hibernate (it needs the annotation processor configured, see the guide).

What to Expect

What you get

  • APIs you already know
  • Fast feedback: dev mode, Dev Services, continuous testing
  • Fast startup and low memory usage
  • An active, open community

What you don’t

  • A fix for technical debt
  • A one-button migration
  • Every library working in native mode

Native mode: third-party libraries that rely on reflection, dynamic class loading or runtime code generation need extra configuration, and some don't work at all. Libraries with a Quarkus extension are handled for you. Even then a class can slip through: my JSON-B adapter needed @Singleton to work in native.
